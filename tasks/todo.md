# iOS アプリの UI/UX 改善（第2ラウンド）

「より見やすく、使いやすくしたい」の続き。今回は最初に
「世の中の優れたアプリのデザインは iOS 標準に準拠した結果なのか」を調べ、
その答えから作業の範囲を決めた。

## 調査：優れたアプリは「標準に準拠した結果」なのか

答えは **違う。ただし「標準を外した結果」でもない。層が分かれている。**

Apple Design Awards 2026 の評価文には「HIG に準拠している」という言葉が
一度も出てこない。褒め言葉は2種類に割れる。

- **中身の表現**：Tide Guide「custom animations」「空の色に合わせたパレット」、
  grug「落書き風の完全自作ビジュアル」、Moonlitt「best-in-class Liquid Glass
  integration と easy onboarding」
- **標準の仕組みを使い切ったこと**：Inclusivity 受賞の Guitar Wiz は
  「VoiceOver / Dynamic Type / Increased Contrast / Differentiate Without Color 対応」

実務側の見解も一致している。標準コンポーネントを自作に置き換えると
VoiceOver・状態変化・ハプティクス・Dynamic Type 追随を全部作り直すことになり、
たいてい劣化する。これは第1ラウンドで BiteLog 自身が踏んだ道でもある。

> 標準は**土台**。差は**中身の見せ方**で出す。
> 優れたアプリは「準拠したから良くなった」のではなく、
> 土台を標準に任せたぶんの労力を中身に注げた。

出典:
- https://developer.apple.com/design/awards/
- https://developer.apple.com/design/human-interface-guidelines/
- https://developer.apple.com/documentation/TechnologyOverviews/adopting-liquid-glass

## 方針（ユーザー確認済み）

- A. 土台に残っている穴を塞ぐ（標準に合わせるだけ。自作の余地がない）
- B. 中身の見せ方で差を出す（栄養データの読ませ方）
- 言語切替の `exit(0)` は廃止してよい
- 広告バーの位置・見た目は調整してよい（表示頻度と掲載面は変えない）

## レビュー

コミットは9本。土台 → 中身 → 実画面 → 実データで見つかった分、の順。

1. `8b40148` 通信の失敗を黙って飲み込まない
2. `2fc9c9d` OSが用意している仕組みに乗り切る
3. `9943762` 栄養データを読める形にする
4. `16cde90` 実画面でしか出ない崩れを直す
5. `cdf451e` 調査結果と詰まった点を記録
6. `557923c` 目標までの残りを出す
7. `60131f8` 写真解析の結果を既存の食品と突き合わせる
8. `1d2d73e` 候補の食品名を大きな文字でも最後まで出す
9. `6a85a5d` 記録の時刻を画面の状態の副産物にしない

### 本番データを見て分かったこと

途中で本番の D1 を集計し、仮説を4つ取り下げた。

- 「9項目フォームが壁」→ 未使用の食品マスタは 8件 / 3,371件、0.24%
- 「オンボーディングが無いから続かない」→ 3,569日中3,564日を記録している
- 「新規ユーザーの検索が働いていない」→ 0件にはならない。並び順が
  登録順に落ちるだけで、「卵」43件なら1件目は「ゆで卵」だった
- 「2人目が定着した」→ 作者本人のテストアカウントだった

代わりに出てきたのがこの2つ。

- **AI 写真解析が記録のたびに食品マスタを作る。** 400件中361件が一度きり。
  写真223件のうち113件は同じものの撮り直しで、同じおにぎりが
  「NL…」「国産…」で3行に割れていた。数値は3回とも一致していたので、
  失敗していたのは AI ではなく「必ず作る」ロジックのほう
- **timestamp の47%が00時台。** 画面の状態がそのまま保存されていた

### 直した実害

- 編集を保存できなくてもシートが閉じ、保存したつもりになれていた
- 食品一覧・追加シートが通信失敗時に「1件も登録されていません」と出ていた。
  登録済みの食品を作り直す操作に直結する
- その日のログの読み込みに失敗すると「何も食べていない日」に見え、
  二重記録を誘発していた
- 食品の削除が失敗しても行を戻さず、消えたように見えて消えていなかった
- 目標値の保存で PUT が4本並走し、最後に返った応答で他の3つが巻き戻りえた
- 追加シートは行タップで即保存なのに取り消す手段が無かった
- `accessibilityReduceMotion` / `colorSchemeContrast` がコード中に1件も無かった
- 統計の PFC バランスが `.blue` / `.yellow` / `.green` 直書きで、
  `Nutrient.swift` が「白背景でコントラストが足りない」と書いている当の色を使っていた
- 言語切替でアプリを `exit(0)` で落としていた

### 実画面でしか出なかった分（コミット4）

部品単体の描画では出ず、モックAPIで通して初めて分かったもの。

- 追加シートの読み込み失敗が無言だった
- 広告の地が高さぶんしか無く、タブバーの裏で行が見切れていた
- スクロールできるグラフでは標準のタップ選択がスクロールに吸われる
- 吹き出しの半透明材質が下の折れ線の色を拾う
- 設定の言語の行だけラベルまで着色されていた
- AX5 で統計画面が読めない（目盛りが重なる・日付が切れる・期間が3行）

## 残っている確認

- 設定アプリに「優先する言語」が出て切り替わることの実機確認

## 別 issue に切り出したもの

- HealthKit 連携と体組成画面
- 目標を体重の推移に連動させる
- AI が一皿まるごとを1件にするときのマスタの扱い
- 紹介ページが実在しない機能を宣伝している

## 体重計と直結: プロトコル層 (#146)

体重計に触らずに検証できる範囲を先に固める。CoreBluetooth は次段。

- [x] チェックサムは直前までの総和のビット反転
- [x] メッセージに全長とチェックサムが付く
- [x] 壊れたチェックサムを弾く
- [x] 宣言された長さと実際の長さが合わなければ弾く
- [x] 応答コマンドは要求コマンドに 0x80 を立てたもの
- [x] TLV はタグごとの固定長で切り出す
- [x] 未知のタグは読み飛ばさずエラーにする（機種差を黙って落とさない）
- [x] 20バイトのフレームに分割する（offset は16刻み、seq は共通）
- [x] フレームを組み直すと元のメッセージに戻る
- [x] 測定データの TLV から9項目を取り出す
- [x] 日付は 2000-01-01 からの日数、時刻は 0.5 秒刻み
- [x] 筋肉スコアは最上位ビットが符号

テストの入力は架空の値を自分でエンコードして作る。実機のトレースは
ターミナル内でのデコード確認にだけ使い、リポジトリには入れない。

### レビュー

`BiteLog/Utilities/TanitaProtocol.swift` と `BiteLogTests/TanitaProtocolTests.swift` を追加。
テスト19件すべて通過。

- `TanitaMessage`: 全長・コマンド・チェックサムの組み立てと読み直し
- `TanitaCommand`: 測定1件を取るまでの9コマンド。応答は要求に 0x80 を立てたもの
- `TanitaField` + `TanitaTag.valueLength`: 46タグ分の値の長さ表。
  未知のタグはエラーにする。長さが分からないと後続の切り出しが全部ずれるため
- `TanitaFraming`: 20バイトへの分割と、notify で届く断片の組み立て
- `TanitaBodyMeasurement`: 9項目 + BMI + 身長 + 測定日時

テストの入力は仕様どおりに組み立てた架空の値。実機トレースのバイト列でのデコード確認は
手元で行い、9項目×2件がサーバー側の記録と一致することを確認した。リポジトリには入れていない。

次は CoreBluetooth 側。ATTハンドルとUUIDの対応、アプリ識別子に任意の値が通るか、
個人データ書き込みが必須かは実機で確かめる。

## 体重計と直結: CoreBluetooth 層 (#146)

やり取りの手順は CoreBluetooth から切り離し、実機なしで検証できる形にする。

- [x] 接続したらアプリ識別子を名乗る
- [x] 時計を合わせる（起点からの日数と半秒刻みの時刻）
- [x] 機器情報と個人データを読む
- [x] 測定待機に入り、応答が返ったら件数を取る
- [x] 件数が0なら引き取らずに終える
- [x] 溜まっている件数だけ繰り返し引き取る
- [x] 待っていない応答が来たら止める
- [x] 測定データが読めなければ止める
- [x] 識別子は端末ごとに固定する
- [x] CoreBluetooth 側の橋渡し（探索・接続・購読・フレームの送受信）
- [x] ボンドしていないときの案内（ペアリングモードの入り方）
- [x] `NSBluetoothAlwaysUsageDescription`

### 実機でしか確かめられないもの

- ATTハンドルと5本のキャラクタリスティックUUIDの対応。書き込みが `5107` か `5108` か、
  応答が `510D` `510E` `510F` のどれで返るか
- アプリ識別子に任意の値が通るか
- 個人データの書き込み（`10 02`）を飛ばしても測定に進めるか
- 未送信データが2件以上あるときの `30 10` の引数の意味

### レビュー

`TanitaSession` が手順を持ち、`TanitaScaleConnection` が CoreBluetooth との橋渡しだけをする。
手順は純粋な状態遷移なので、応答を組み立てて渡せば実機なしで検証できる。
テストは合計69件すべて通過（うち今回追加が15件）。

体重計の登録先は1台しか持てないため、ペアリングの移行はまだ行っていない。
UI と `POST /api/body-measurements` への送信も未着手。

## 体重計と直結: 取り込み画面 (#146)

実機で試すには押せる入口が要る。設定から体組成計につないで、受け取った測定を
サーバーへ送るところまでをつなぐ。

- [x] `BodyMeasurementCreateDTO` — 受信した測定をサーバーの17列に合わせる
- [x] 計測時刻の秒を切り捨てる（CSV経路と二重に入らないように）
- [x] 日付は計測した地域の暦日で送る
- [x] `inputMethod` で経路が分かるようにする
- [x] `POST /api/body-measurements`。409 は重複として数える
- [x] 取り込み画面。状態、受け取った測定、保存件数と重複件数
- [x] 設定のデータ管理に導線を置く
- [x] 日本語と英語の文言

### レビュー

テストは合計76件すべて通過（今回追加が6件）。変換は純粋な処理なので単体で確かめられる。

画面そのものと BLE の往復は実機でしか確かめられない。シミュレータには Bluetooth が無い。

残りはペアリングの移行だけになった。これはヘルスプラネットへの蓄積が止まる操作なので、
実機で往復を確かめ、戻せることも確認してから踏む。
